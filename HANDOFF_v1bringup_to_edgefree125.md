# Hardware hand-off: `v1-bringup` → `feature/k16-cfglut5-edgefree-125mhz`

Date: 13 September 2026. Comparison commits: `v1-bringup` = `fb66066`
(report: apply correction queue + M7/M8 evidence) vs
`feature/k16-cfglut5-edgefree-125mhz` = `00a6e11` (Release EF125K16N3W32R01).
All differences are recorded from `git diff fb66066..00a6e11` and the routed
implementation reports in `work/release_125/artifacts/`. Scope: the complete
hardware project (system blocks + core accelerator), verification, release
infrastructure, and software-adjacent deltas.

## 1. Lineage context (read first)

`v1-bringup` and this branch are **sibling lineages**, not parent/child.
`v1-bringup` carries the M5–M8 release line of the older accelerator
(multiplier datapath, multi-profile runtime switching). The K16 CFGLUT5
architecture was developed on a separate branch (`feature/k16-cfglut5-exact`,
commit `b831072`) which is **not an ancestor** of `v1-bringup`; the EdgeFree
edge-bubble work and the 125 MHz closure continued from there. This branch
therefore *replaces* the whole datapath while preserving the system
integration and software contract around it.

## 3. Core datapath: full replacement

### 3.1 Removed engine (v1-bringup)

`conv_channel.vhd` (196 lines): classic four-stage inferred-multiplier lane
(S1 `N*N` unsigned x signed multiplies, S2/S3 add-tree, S4 postprocess;
4-clock latency). `conv_engine.vhd` (89 lines): simple per-channel
instantiation.

### 3.2 New engine (this branch)

- `cfglut5_kcm.vhd` (**new**, 82 lines): exact constant-coefficient
  multiplier from two CFGLUT5 primitives per output pair; the weight byte is
  compiled into a 32-bit truth table at configuration time.
- `cfglut5_bitheap_3x3.vhd` (**new**, 3,776 lines, generated by
  `scripts/generate_cfglut_bitheap.py`): one fused signed Dadda compressor
  tree per channel over the nine radix-16 partial products; structural
  LUT6_2 netlist, no DSPs.
- `conv_channel.vhd` (196 -> 208 lines): now instantiates the CFGLUT5 KCM +
  bit heap. Five stages, II unchanged at 1:
  S1 CFGLUT lookup + Dadda levels 1-3, S2 levels 4-6 + two-row register,
  S3 carry-propagate sum + bias, **S4 arithmetic shift + discarded half-bit
  register, S5 round-half-up increment + saturation + optional ReLU**
  (the old single S4 was split for 8 ns closure). Includes the
  sign-extension guard: for shift > 25 (accumulator width) the discarded
  half-bit is the sign bit instead of an out-of-range index. The old code
  silently produced a wrong result for shifts 26-31 (out-of-range read,
  'U' semantics, no round-up); the new behaviour is verified against the
  Python/64-bit reference for all 32 shift encodings.
- `conv_engine.vhd` (89 -> 244 lines): 16 channels, runtime CFGLUT
  configuration serial load (4,608 clocks per full 16x9 reload) with
  `cfg_pending`/`cfg_ready` guard so START/new writes wait until the final
  truth bit has actually reached the CFGLUTs, and **four local registered
  window-distribution banks** (`window_banks`, 4 channels per bank,
  `dont_touch`) so the window fanout at 8 ns is split by construction.
- Net arithmetic effect: latency 4 -> 6 clocks (input bank + S4/S5 split),
  II still 1, results bit-exact vs the golden model (1,007-test reference +
  `tb_cfglut5_pipeline` over 32 shifts x 16 bias cases x 2 ReLU modes).

### 3.3 Window generation

`window_generator.vhd` (136 -> 139 lines): functionally the same SRL
line-buffer design as before; cosmetic/comment changes only. Distribution
fanout is handled by the engine's window banks (3.2), not by replicating
line history.

### 3.4 Wrapper and top (edge prefetch + coefficient path)

- `conv_axis_wrapper.vhd` (722 -> 728 lines): input frontend readiness is
  now driven by the convolution top's `pixel_ready` (edge prefetch), the
  wrapper's output accounting observes registered accept events, and the
  module accepts/passes the branch identity generic.
- `conv_top.vhd` (484 -> 588 lines): `C_WINDOW_PREFETCH` elastic window
  slot (`window_ce = run and (ce or not window_valid)`), `pixel_ready`
  output, coefficient write-through path to the engine's serial
  configurator, and the completion/accounting boundary changes below.
- `axi_lite_ctrl.vhd` (1,993 -> 2,115 lines): the M4 lifecycle contract
  (IDLE/CONFIG/RUN/FAULT, discovery, quotas, fault accounting, abort,
  reset) is preserved, with three additions for 8 ns: AW/W capture moved
  after registered-transaction decoding (raw SmartConnect payload no
  longer feeds the command cone), a one-cycle completion-check stage
  (`output_check_valid_q/last_q`) that keeps the counter adders out of the
  DONE cone, and `CFG_BUILD_ID` propagation replacing the hardcoded legacy
  build string.

### 3.5 Unchanged system blocks (byte-identical)

`axi_stream_input_frontend.vhd` (716), `axi_stream_output_serializer.vhd`
(642), `coeff_bias_shift_regfile.vhd` (322), `sync_fifo.vhd` (85), and
`Zedboard-Master.xdc` are unchanged from `v1-bringup`. The M4 software
contract (accelerator `0x43c00000`, DMA `0x40400000`, 64 KiB UIO mappings,
u-dma-buf layout, TKEEP/TLAST rules, quotas, fault/abort/reset semantics)
is preserved.

Direct apples-to-apples: the same CFGLUT5 architecture at 100 MHz
(sibling release branch `feature/k16-cfglut5-edgefree-100mhz`) measures

geometry: K=4, 640x480), so it is not numerically comparable.

FOM (announcement form: FoM = Throughput / (P x (LUT + 50 DSP + 100 BRAM)),
throughput in output pixels per cycle; weighted resources 13,266 at
100 MHz vs 13,372 here; sustained 4 px/cycle through the serializer,
peak 16 px/cycle at the core):

| Basis | 100 MHz | 125 MHz | Delta |
| --- | ---: | ---: | --- |
| Announcement units, system, sustained | 1.684e-4 | 1.658e-4 | -1.5% |
| Announcement units, system, peak core | 6.736e-4 | 6.632e-4 | -1.5% |
| Announcement units, core-only (8,569 vs 8,241 LUTs) | 9.93e-3 | 1.011e-2 | +1.8% |
| Per-second basis (px/s per W-resource), system | 16,837 | 20,727 | +23.1% |

In the announcement's literal px/cycle units the FoM is
frequency-independent, so 125 MHz is flat to -1.5% system-wide (power
1.791 -> 1.804 W, LUTs +106). On the per-second basis the gain is +23.1%
(400 M -> 500 M output pixels/s). State the chosen basis in any report.

## 8. How 125 MHz was reached (the journey, including the failed attempt)

1. Clock experiments: an exact-120 MHz MMCM insertion was tried first and
   removed; the user approved **native PS FCLK 125** (`PCW_ACT_FPGA0...`
   verified 125.000). Wrapper behavioral tests moved to an 8,000 ps period.
2. Architecture for 8 ns: five-stage arithmetic split (S4/S5), controller
   AW/W capture restructure + completion-check stage, `cfg_pending` guard.
   With those, the first 8 ns route missed by **-0.250 ns** across 202
   endpoints.
3. Path analysis (`scripts/analyze_125_paths.tcl`): the failures were
   distribution-fanout routing - window/line-buffer registers broadcasting
   to 16 channel bitheaps (~80% route delay) and the `cfg_weight`/`cfg_data`
   configuration fanout (CARRY4 chains).
4. A broad `MAX_FANOUT` attribute trial made things worse
   (**-0.574 ns, 855 endpoints**, window generator 2,388 FFs) and was
   reverted. The adopted remedy is the engine-local registered window
   banks (3.2) plus `cfg_pending`, which closed timing at **+0.201 ns**
   and actually *reduced* wrapper LUTs (controller restructure 1,913 ->
   1,568 LUTs in the equivalent comparison).
5. Per Astra's inspection (recorded in the 120MHz plan): the broad
   attribute trial must not be re-applied as-is; the engine banks are the
   standing solution.
